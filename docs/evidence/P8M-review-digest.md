## How I decided

Calibration you chose: **decisive** — approve where the row's own text supports the proposal; reserve
`needs_more_evidence` for rows the text genuinely cannot settle.

- **approve** — every proposed value is supported by the row's own cells or summary.
- **revise** — a specific value is wrong or over-claimed *and* the row supports a named replacement (given in the rationale).
- **reject** — the proposal is unsupported and there is no defensible replacement.
- **needs_more_evidence** — the row cannot settle it; the value stays unknown. A completed outcome, not a deferral.
- **not_applicable** — used on exactly the 158 rows whose `correction_candidates_json` is `[]`, and nowhere else.

Two limits, both recorded in the affected rationales:

1. **The topic vocabulary is closed and not supplied.** I only ever proposed replacement topics that
   already appear somewhere in the 197 rows. I never invented a value — so where a row's real
   eligibility driver has no available topic, the rationale says so instead.
2. **The review workbook exposed 7 of the Master Database's 15 source columns.** Decisions were first
   made without the other 8, then re-checked against the full source once it was supplied; ten rows
   changed as a result (see 2g). Official verification is still outstanding on all 197 rows — column A
   is `Last Updated`, not a URL — so approved corrections remain recommendations, not accepted facts.
